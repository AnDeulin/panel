# Проект переиспользуемого компонента

Это техническая спецификация. Статус работающего компонента устанавливается после реализации
и проверки выбранного подключения, модели и инфраструктуры.

## Граница компонента

Встраиваемый интерфейс на сайте обращается к серверу проекта. Сервер определяет состояние
разговора, лимиты, вариант эксперимента, подтверждённые условия продукта и передачу человеку.
Адаптер модели получает необходимый контекст и возвращает структурированный результат.
Хранилище и события привязаны к проекту. Подтверждение оплаты поступает из доверенного источника.

Интерфейс может быть встроенным блоком Typebot или отдельным небольшим JavaScript-компонентом.
Для проекта, где уже используется Python, можно сохранить этот язык на сервере. Состав служб
и способ размещения выбираются по доступной инфраструктуре и требованиям к данным.

## Минимальный контракт

Конфигурация проекта содержит идентификатор, версию сценария, допустимую тему, утверждённые
условия продукта, схему результата, адрес обращения к человеку, размещение модели и лимиты.
Доступ к модели находится на сервере. Данные другого проекта изолированы.

Маршрутизация учитывает намерение и стадию человека. Схемы результата могут различаться
для новой ниши, канала, знакомства с ИИ и улучшения текущей работы. Общая часть фиксирует
цель, подтверждённые вводные, допущения, полезный результат и следующий шаг. Заполнение
сведений, не влияющих на текущий выбор, допускается пропустить.

Состояния разговора могут включать сбор вводных, выдачу результата, уточнение, передачу человеку
и завершение. Режим человека сохраняется до явного возврата автоматических ответов.

Каждый запрос содержит идентификатор сеанса, уникальный идентификатор операции и ожидаемую
версию состояния. Повтор той же операции возвращает прежний результат. Параллельная операция
получает понятный ответ о текущей обработке. После сбоя сохраняется возможность продолжить.

Модель возвращает ответ, предложенные сведения и карточку результата по проверяемой схеме.
Подтверждение сведений, вариант эксперимента, квоту и условия продажи устанавливает сервер.
Вывод модели отображается как текст. Ссылки действий берутся из конфигурации.

Пример минимальной карточки результата для диагностики задачи.

```json
{
  "task": "Описание одной выбранной задачи",
  "input": "Какие обезличенные данные нужны",
  "sample": "Небольшой пример результата",
  "first_step": "Действие, доступное сейчас",
  "check": "Как проверить полезность",
  "assumptions": ["Что требуется уточнить"]
}
```

Для проверки ниши вместо полей входа и образца подходит гипотеза, план первого теста и
критерий решения. Для знакомства с ИИ подходит краткое объяснение и небольшая проба.
Сервер проверяет соответствие результата схеме выбранного намерения.

## Лимиты и устойчивость

Квота ограничивает законченные разборы и дополнительные уточнения. Параллельно ограничиваются
частота запросов, длина ввода, размер контекста, выход модели и общий расход проекта.
Для анонимного посетителя совмести идентификатор браузера и временные ограничения по сети.
Учитывай общие адреса сети у разных людей. При злоупотреблении можно добавить проверку на человека.

Сбой модели не выдаётся за израсходованный полезный разбор. Реально выполненные обращения
к поставщику учитываются в расходах. После лимита доступны уже полученный результат и контакт.
Резервирование бюджета перед вызовом предотвращает перерасход при параллельных запросах.

## Память

Контекст сеанса имеет ограниченный срок хранения. Для сохранения между визитами пользователь
видит, какие сведения сохраняются, и может изменить или удалить их. У записи есть проект,
источник, время, срок и статус подтверждения. Отзыв сохранения распространяется на связанные копии
по выбранным правилам хранения. Данные для контроля расходов могут быть агрегированы отдельно.

Политика локализации и передачи данных проверяется до работы с реальной перепиской. Статус
stateless у API описывает ведение контекста, а правила хранения устанавливаются политикой поставщика.
Для российского проекта используй [отдельный проект хранения](data-architecture-ru.md).

## События и связь с продажей

В журнале событий нужны время, проект, версия сценария, версия эксперимента, вариант,
псевдоним участника, источник трафика, тип события и идентификатор результата.
Свободный текст диалога сохраняется в отдельном защищённом хранилище с заданной целью.

Минимальные события включают назначение варианта, открытие, начало, готовый результат,
подтверждение пользы, переход к человеку, бронь, полную оплату, возврат, ошибку и ограничение квоты.
Платёжные события принимаются из проверенного сервиса либо вносятся организатором после проверки.
Обновления имеют идентификатор для защиты от повторного учёта.

При переходе в мессенджер передаётся случайный код обращения. Он связывает последующую
подтверждённую оплату с вариантом. В адресе перехода достаточно кода и нейтрального контекста.

## Приёмка

Проверь получение результата, повторный запрос после сетевого сбоя, параллельные запросы,
лимиты, отказ модели, сохранение варианта, передачу человеку, возврат ИИ, исправление и удаление
памяти, подтверждение оплаты и повтор платёжного события. Проверка модели включает целевые,
нецелевые, неполные и провоцирующие запросы на утверждённых или синтетических примерах.

Живой пилот требует размещения, модели, способа обработки данных и ответственного за обращения.
Для ранней проверки достаточно одного сценария. Присоединение дополнительных проектов
проходит через отдельную конфигурацию, основания данных и проверку результата.
